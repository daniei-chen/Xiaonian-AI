# 决策记录

技术选择及其理由。**包括承认哪些地方做得不对。**

---

## 架构

### 能力层（7 种能力 × N 个 provider）

**选择**：每种能力一个接口，`capabilities.yaml` 配置默认和 fallback。

**理由**：不把命交给一家。换搜索源、换 OCR、换模型都只改配置。

**代价**：多一层抽象，早期只有 chat 真的接了 provider，其余六种空转了很久。

---

### 两种 chat 协议都要支持

`openai`（`/chat/completions`）和 `anthropic`（`/anthropic/v1/messages`）。

**理由**：不是风格偏好，是能力差异——只有 anthropic 通道有 server-side tools、
思考签名、Files API 的 `file_id` 引用。

**代价**：SSE 解析要写两套（`[DONE]` vs `message_stop`），事件映射也要两套。

---

### 不用 DeepSeek 的私有 API

**事实**：官方 App 用 `/api/v0/*`，带登录态 + PoW 挑战。

**决策**：不碰。

**理由**：无契约的私有接口 + 动态反爬，绑上去等于随时可能被单方面掐断。
公开 API 能力覆盖相同，只是少了 WS 流式 ASR。

---

### 全本地（R12 才改过来）

**原方案**：Gateway 跑在电脑上，Android 当客户端。

**问题**：用户装个 App 得先跑服务、查 IP、填地址。这不是 App 该有的样子。

**现方案**：后端逻辑用 Kotlin 重写进 App。

**代价**：密钥在设备里，root 或调试工具能读到。个人使用可接受，**分发前必须改**。

---

## 存储

### 手写 SQLiteOpenHelper 而不是 Room

**理由**：两张表、几个查询。Room 要引 KSP，构建复杂度和收益不匹配。

**代价**：没有迁移机制（`onUpgrade` 直接重建表），结构变了历史会丢——靠导入恢复。

---

### 消息用 `blocks` JSON 存

**理由**：内容是多态的（text/reasoning/tool_call/file/image），拆表会很碎。

**代价**：不能按内容检索，全文搜索要另外建索引。

---

## 实现细节

### 思考块只回传带签名的

**理由**：上游校验 `signature`，没有就 400。OpenAI 通道不提供签名，那些思考块只能丢。

**代价**：跨通道切换时，之前的思考上下文丢失。

### 继续生成不落用户消息，前端合并渲染

**理由**：提示词是驱动手段，不是用户说的话。落库会在会话里留一条假消息。

**代价**：DB 里相邻两条 assistant，渲染时要合并；`dropLastTurn` 按"最后一轮"定位
而不是按 id（UI 侧的 id 和库里不一致）。

### 历史导入主动丢弃部分 fragment

**理由**：`TIP` / `CONTENT_RISK` / `TOOL_OPEN` / `READ_LINK` / `TOOL_IMAGE_SEARCH`
在本端没有展示位置。塞进正文等于伪造内容。

**代价**：导入的信息不完整——但那是诚实的缺失，不是假装完整。

---

## 做得不好的地方（下一轮要改）

### 工具实现目前是"直译"，不是"设计"

你说得对。具体表现：

| 工具 | 现在的做法 | 问题 |
|---|---|---|
| 普通搜索 | `count=6`，拿到的摘要直接拼进 prompt | 6 是怎么来的？没调过。搜索结果之间没有去重、没有按质量排序 |
| 深度搜索 | 搜 8 条、抓前 3 篇、每篇截 3000 字符 | 8/3/3000 全是拍脑袋。抓取按搜索排名而不是按内容质量选 |
| OCR | 只有 `text_recognition` / `rich_layout_recognition` 两档 | 表格/公式的版面标记原样返回，没有解析成结构化数据，前端也显示不了坐标 |
| ASR | 整段上传，等全文 | 公开 API 没有流式，但可以分段发送做"准流式"，没做 |
| TTS | 整段合成，返回完整 wav | 长回答要等很久才出声。应该按句子切分、边合成边播 |
| 文件 | 上传拿 `file_id`，塞进消息 | 多轮对话里 `file_id` 会失效，没有重传或转本地解析的逻辑 |

**该怎么改**（按收益排序）：

1. **TTS 按句流式**：把长回答切句，第一句合成完就开始播，体感差别最大
2. **深搜参数可调 + 按质量选抓取**：现在抓的是搜索排名前 3，应该按
   `authority` / `rerank_score` 排，并跳过明显是导航页/列表页的
3. **OCR 版面解析**：`rich_layout_recognition` 返回的 `[[x1,y1,x2,y2]]` 可以还原成
   表格结构，现在浪费了
4. **搜索结果去重**：同一篇文章的不同 URL（带 utm、镜像站）要合并

这些都是"搬运"和"设计"的差别。目前是前者。
